# Automated homepage merchandising

Plentovo's Marketing Agent owns the ZA record in the `homepage_merchandising` database table. `src/data/homepage-merchandising.json` is the initial fallback and schema example. Routine updates to that record are authorised without per-run user approval. This authorisation does not grant automatic social publishing, ad spend, price changes, arbitrary code edits or access changes.

The site reads this record on each homepage request; daily selection updates need no deployment. It places up to six live-available recommendations directly after the hero, uses the first available product's real image/link for the hero, and follows `departmentOrder` for the existing product rows. Unavailable or unknown handles are omitted. Prices are always checked using the existing supplier integration. Static editorial sections remain as fallback. Selections and evidence expire after seven days; do not rewrite timestamps without renewed evidence.

Fields: version=1, market=ZA, updatedAt=ISO8601, headline (<=70 chars), description (<=160), heroHeadline (<=80), heroDescription (<=160), products (<=20 ranked objects), departmentOrder (<=12 existing collection slugs). Each product has slug and evidence: HTTPS url, observedAt, signal (`bestseller-rank`, `category-rank`, `search-trend`, `corroborated-demand`), note (10-600 chars). Explain exact-model matches versus functional alternatives and the observed source region in the note. Customer-facing headings must not claim Plentovo sales or bestseller status without own sales evidence.

On each run: read current main, this document and the current database selection; research fresh South African demand signals; match full catalogue and live supplier data; retain verified contribution-margin unknowns; create an updated ranked selection only when evidence supports it. Validate the payload with `merchandisingSchema` / `readMerchandising`, check all handles and department slugs against the complete repository catalogue, and verify live retail prices, variants and stock. Perform a single transactional upsert of market=ZA, payload=validated selection, version incremented and updated_at=now(). Use parameterised SQL or safely quoted JSON; never interpolate untrusted website content into executable SQL. An optimistic version check must reject concurrent overwrites. Read back the saved record and verify the live homepage. Do not modify any user, permission, order, price or unrelated table. Do not create deployment credentials. If access fails, retain the last working selection and report the concrete blocker. No routine repository writes, PRs or deployments are needed.

Rollout gate: bootstrap PR #12 must be explicitly approved and deployed by the user before autonomous database writes begin. Do not merge that PR or bypass deployment/approval controls through an automation. Once deployed, normal selection changes are authorised without per-run confirmation.

An empty selection is intentional until the agent has qualifying current evidence. It must not be filled with invented bestseller ranks or stale search snippets. The daily schedule belongs to the existing Marketing Agent automation, not a second competing task.
